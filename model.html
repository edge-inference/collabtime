01 / One request

Ready, start,
finish.

Every piece of work gets three times. An inference, a prompt preparation and a message on the link are all handled the same way.

Ready. A request is ready at the later of two events: its input has arrived, and every step it depends on has finished.

Start. The resource that runs it decides when it may begin. That decision is the serving rule. It looks at the work already queued and at how much the resource can run at once.

Finish. The start plus a predicted run time. The prediction comes from a cost model fitted to measurements of the target device.

ready q = later of ( a , finish of earlier steps )
start s = admit ( q , queue , capacity )
finish f = s + predicted run time

Equation 2 in the paper. A serving rule enters in the middle line: it decides which work the resource runs, and when.

The serving rule moves the finish.

One Thor module runs the action policy, System 1, and the reasoning model, System 2. The request is ready at the same moment in all three cases. Only the rule for sharing the GPU changes.

These three latencies are measured on the board, not predicted. The scheduler comparison runs the real scheduler on the real module and does not rely on the timing model.

02 / Shared server

Many robots,
one GPU pass.

A reasoning server works in iterations. Each iteration carries a batch: some requests are reading their prompt, others are writing their answer.

Start. An iteration starts at the later of two events: its batch has been formed, and the previous iteration has finished.

Finish. The start plus the predicted time for that batch. The time depends on what the batch holds: how many requests, how many tokens, and which of them are reading or writing.

start sk = later of ( batch k formed , fk−1 )
finish fk = sk + predicted time of batch k

Equation 3 in the paper. A request that joins late shares the pass with those already inside, which is why one robot’s wait depends on the others.

03 / The loop

System 2 decisions and
when robots can use them.

The loop of Figure 4 couples the task simulator to the hardware model. In this example, System 2 generates each decision; hardware modeling determines when the robot can use it.

Which decision does System 2 generate?

System 2 inference runs on the simulation host to generate the decision. Host execution time does not advance simulated time.

When may the robot use it?

The resource model simulates the target CPU, GPU and link. The decision remains pending until its modeled release time.

  1. while worlds remain
  2. P ← Complete(P, R.advance(t))
  3. U ← Admit(U, P.PopReady(t))
  4. (U, a, N) ← NativeStep(W, U, P, t)
  5. X ← Capture(N); (Y, D) ← EvaluateModel(X)
  6. for each robot r in N
  7. P[r] ← (Y, ∞); R.submit(r, t, D)
  8. StepWorlds(W, a, Δ); t ← t + Δ
  9. P ← Complete(P, R.advance(t))
  10. F ← Finished(W, t); W ← W \ F
  11. P ← Discard(P, F)
  12. R.drain()

04 / In step

Two clocks,
one time.

The world and the hardware model are two simulations. At every tick the hardware model is moved forward to the world’s time, and no further.

Not ahead of the world. A request that arrives later can still slow one that arrived earlier. If the hardware model ran robot A’s request straight to its end, robot B’s request would arrive too late to count, and A would receive its model output one tick too early. Switch the replay to “Running ahead” to see it.

Not behind the world. A model output must be released at the first control tick at or after its modeled completion time plus any dispatch delay.

So a finish time is never fixed when a request arrives. It is settled tick by tick, as the world shows what else is asked.

Robot A asks at 0 ms. Alone, its request would take 180 ms.

05 / Next tick

Model outputs take effect
at a control tick.

A robot applies commands on its control clock. When inference completes between two ticks, the output is applied at the next one.

acts at the first tick at or after ( finish + dispatch delay )

Equation 4 in the paper. This rounding maps completion and dispatch time to a control tick. A faster control clock reduces the wait before the robot can apply the output.

The dispatch delay is zero in this picture.

How the model is checked

The native co-execution tests use observed completion times instead of modeled completion times: the simulator advances at the command cadence while inference runs on Thor. That separates a measured benefit of an allocation from a prediction of the timing model. See the findings.

06 / Scheduler

Hold System 2 only
as long as needed.

On one module the two models share a GPU. For each action inference the scheduler decides whether System 2 must wait, and for how long.

Estimate. The scheduler keeps two running estimates of the action latency: with System 2 free, and with System 2 held.

Compare. The target is 0.8 of the latency budget. If the free estimate is within the target, System 2 keeps running.

Hold. Otherwise System 2 is suspended for a share of the action inference. The share grows as the free estimate rises above the target. A full hold lasts until the action completes.

share f = ( free − 0.8 × budget ) ÷ ( free − held ) + b
hold f × held, with f kept between 0 and 1

Equation 5 in the paper. The term b corrects the error seen under partial holds. This is a feedback heuristic, not a worst-case timing bound. A hold suspends the System 2 process and keeps its model in memory; GPU work already submitted still finishes.

The measured outcomes sit under the replay. With the 250 ms budget the action latency came out the same as with always prioritizing. The looser phase budgets returned it toward time slicing.
